================================================================================
0. RESUMEN EJECUTIVO
================================================================================

Los tres archivos son las tres "caras" del mismo modulo de tickets. Comparten
casi toda la estructura HTML, los mismos CSS/JS y el mismo patron de
funcionamiento; lo unico que cambia es:

    a) El valor de $idPagActual (3 = usuario, 4 = admin, 5 = tecnico).
       Ese numero se usa como discriminador en la clase Funciones para
       decidir QUE tickets contar/mostrar y con que filtro (id_usuario,
       id_tecnico o todos).

    b) La tabla principal que incluyen:
         ticket.php            -> componentes/bloque_tabla_usuario.php
         ticket_asignados.php  -> componentes/bloque_tabla_tecnico.php
         ticket_admin_v2.php   -> componentes/bloque_tabla_adminn.php

    c) El metodo de consulta de la clase Funciones que alimenta esa tabla:
         usuario -> $funciones->ticketUsuario($id, $estado)
         tecnico -> $funciones->obtenerTicketsTecnico($id, $estado)
         admin   -> $funciones->ticketAdministrador($id, $estado)

    d) Las acciones disponibles en la columna OPCIONES de cada fila.

Patron general de las 3 vistas:
    1. session_start() + require conexion.php + require funciones.php
    2. Se instancia $funciones = new Funciones()
    3. Se pinta <head> con librerias (Bootstrap, DataTables, jQuery, SweetAlert2,
       Quill, Font Awesome, Bootstrap Icons, XLSX, Intro.js) + CSS/JS propios
    4. Menu lateral: $funciones->menuLateral2($idUsuarioSession, $idPagActual)
    5. Barra superior: $funciones->cabezera()
    6. Fila de "contenedores de estado" (tarjetas KPI) -> $funciones->contenedorTicket*()
    7. Card con la tabla de tickets (include del bloque_tabla_*)
    8. Offcanvas "Detalle del Asunto" (#offcanvasAsunto)
    9. Div vacio #offcanvasContainerTicket (donde chat_ticket.js inyecta el chat)
   10. $funciones->footer() + $funciones->script()
   11. Bloque <script> inline que:
         - inicializa el DataTable
         - hace polling AJAX cada 3 segundos para refrescar el <tbody>
         - define window.filtrarTickets(estado) y window.mostrarTodosLosTickets()

1. FUNCIONALIDADES PRINCIPALES DE CADA ARCHIVO

--------------------------------------------------------------------------------
1.1  ticket.php   ->  VISTA DEL USUARIO FINAL (solicitante)   idPagActual = 3
--------------------------------------------------------------------------------
Es el panel donde un usuario ve y gestiona SUS PROPIOS tickets (los que el creo,
filtrados por t.id_usuario = sesion).

Funcionalidades:
    - Ver KPIs de sus tickets por estado (Asignados, En proceso, Terminados,
      Demorados/Atrasados). NOTA: la linea de "Recibidos" esta comentada en esta
      vista.
    - Crear un ticket nuevo -> boton "Agregar ticket" que llama
      crearTicketGuadalupe(idUsuarioSession) (modal SweetAlert2 con editor Quill).
      Puede guardarse como TICKET (estado 1) o como BORRADOR (estado 4).
    - Tabla "Tickets creados" (#tablaUsuario) con: N, fecha/hora, De, Asunto,
      Estado, Fec Res, Dias restantes, barra de Progreso (x/4 pasos), Opciones.
    - Ver detalle del asunto en un offcanvas lateral (mostrarOffcanvasAsunto).
    - Ver el ticket completo:
         estado 4 (borrador) -> ticketBorrador(id)   (permite editar/enviar)
         otro estado         -> modalTicketUsuario(id) (solo lectura + timeline)
    - Chat con el tecnico -> cargarTicketConversacion(id, id_usuario, id_tecnico,
      id_estado); badge rojo con cantidad de mensajes.
    - Ver archivos adjuntos -> archivosAdjuntos(id) (badge con cantidad).
    - Calificar el ticket cuando esta Terminado (estado 5) y aun no tiene
      calificacion -> validacionTicketPorUsuario(id, id_usuario, id_tecnico)
      (estrellas 1-4 + comentario). Este es el paso que "cierra" el ciclo para
      el usuario.
    - Auto-refresco de la tabla cada 3 s por AJAX (sin recargar pagina).
    - Filtro por estado al hacer click en la lupa de cada tarjeta KPI.
    - Tour de ayuda con Intro.js (iniciarTour(), actualmente el boton esta
      comentado pero los atributos data-intro siguen en el HTML).

--------------------------------------------------------------------------------
1.2  ticket_asignados.php  ->  VISTA DEL TECNICO            idPagActual = 5
--------------------------------------------------------------------------------
Panel del tecnico: ve los tickets donde el es el responsable
(t.id_tecnico = sesion  AND  t.id_estado != 4  -> nunca ve borradores).

Funcionalidades:
    - KPIs filtrados a SUS tickets (Asignados, En proceso, Terminados, Demorados).
    - Publica en JS global: var nombresession y var idUsuarioSession
      (json_encode) para uso de los scripts.
    - Tabla "Tickets Tecnico" (#tablaTecnicoTicketAsignados) con: ID, fecha/hora,
      De, Asunto, Estado, Fecha respuesta (con subtitulo de dias transcurridos /
      dias totales y dias restantes), Calificacion (estrellas si el usuario ya
      califico), Opciones.
    - Ver ticket -> modalTicketTecnico(id): desde aqui el tecnico COMIENZA el
      ticket (estado 2 -> 3), registra avances (avance_tecnicos) y lo da por
      TERMINADO (estado 3 -> 5) con comentario final.
    - Chat con el usuario -> cargarTicketConversacion(...).
    - Archivos adjuntos -> archivosAdjuntos(id).
    - Si el ticket esta DEMORADO (estado 7): boton para
      reprogramarFechaTicketDemorado(id, fechaActualIso) -> actualiza
      fecha_estimada_admin / reprogramar_ticket.
    - Si esta Terminado y calificado: calificarTicket(id) para ver la
      calificacion que dejo el usuario (solo lectura).
    - Auto-refresco cada 3 s.
    - Filtros de tabla persistentes en sessionStorage
      (clave 'filtrosTablaTecnico': estado, fecha creacion, fecha respuesta).
    - Incluye modal_salir.php (modal de cierre de sesion).
    - CSS <style> embebido que reduce el font-size de la tabla del tecnico.

--------------------------------------------------------------------------------
1.3  ticket_admin_v2.php  ->  VISTA DEL ADMINISTRADOR        idPagActual = 4
--------------------------------------------------------------------------------
Panel de control global: ve TODOS los tickets del sistema
(WHERE t.id_estado != 4, es decir todos menos borradores).

Funcionalidades:
    - KPIs globales: aqui SI se muestra "Tickets Recibidos" (contenedorTicketRecibidos)
      ademas de Asignados, En proceso, Terminados, Demorados.
    - Publica var nombresession y var idUsuarioSession en JS.
    - Activa $GLOBALS['ticketAdminColorColumn'] = true ANTES del include, lo que
      hace que la tabla use un "punto indicador" de color de estado por fila en
      vez de pintar toda la fila del color del estado (modo compacto).
    - Tabla "Tickets Administrador" (#dataTableAdministrador) con: ID, fecha/hora,
      De, Asunto, TECNICO (boton Asignar/Cambiar tecnico o nombre del tecnico),
      Fecha respuesta, Calificacion, Opciones.
    - Asignar / cambiar tecnico -> asignacionTecnico(id_ticket): modal SweetAlert2
      grande. Carga datos del ticket, lista de tecnicos (avatares clickeables),
      categorias; al cambiar la categoria puede autoseleccionar el tecnico
      sugerido para esa categoria (tecnico_por_categoria.php). Guarda con
      guardar_responsable_ticket.php (id_responsable, comentario, categoria,
      idTicket). Al asignar, el ticket pasa a estado 2.
    - Ver ticket -> modalTicketAdministrativo(id) (lectura completa + timeline).
    - Archivos adjuntos -> archivosAdjuntos(id).
    - Calificacion:
         * si el ticket esta en estado 5 y tiene calificacion, se renderiza un
           contenedor <div class="contenedor-estrellas-admin" data-ticket-id="..">
           que JS rellena via modelos/rescatar/calificacionUsuario.php
           (funcion mostrarEstrellas / renderizarCalificacionesTablaAdmin).
         * calificarTicket(id) abre modal de solo lectura.
    - Aviso "ultimo dia" al tecnico: si el ticket esta En proceso (3), le queda
      1 dia y tiene tecnico -> boton enviarAvisoUltimoDiaTecnico(id) que envia
      correo (modelos/guardar/avisar_ultimo_dia_tecnico.php).
    - Menu contextual (tres puntos) por fila:
         * Eliminar   -> eliminarTicketDesdeMenu(id)   (soft delete, log_eliminacion_tickets)
         * Fusionar    -> fusionarTicketDesdeMenu(id)
         * Historial   -> estadistica/vida_ticket.php   (link, actualmente sin ?id_ticket)
    - Filtros avanzados de tabla: Estado, Fecha creacion, Tecnico
      (incluye opcion "Sin asignar" = __sin_asignar__), Fecha respuesta.
      Se aplican via un plugin de busqueda de DataTables (ext.search.push).
    - Auto-refresco cada 3 s con guarda "actualizacionTablaEnCurso" para evitar
      solapamiento de peticiones.
    - Incluye modal_salir.php.

    *** OBSERVACION / BUG POTENCIAL ***
    El JS de ticket_admin_v2.php hace  $.post('componentes/ajax/bloque_tabla_adminn.php', ...)
    (doble "n"), pero el archivo real en disco es
    'componentes/ajax/bloque_tabla_admin.php' (una sola "n").
    Salvo que exista un rewrite en el servidor, el polling de refresco de la
    tabla admin devuelve 404 y la tabla no se auto-actualiza (solo se llena en
    la carga inicial por el include PHP). El include de PHP
    ('componentes/bloque_tabla_adminn.php', doble n) si existe y es correcto.

--------------------------------------------------------------------------------
2.1  Metodos de la clase Funciones  (class/funciones.php)
--------------------------------------------------------------------------------

Comunes a las 3 vistas (invocados directamente en el .php):

  $funciones->header()
        Imprime <meta>, <title>SEDUC SPA</title>, favicon y CSS/JS base
        (FontAwesome, Bootstrap 5.1.3, bootstrap-icons, sb-admin-2.css /
        sb-admin-2.min.css, fuente Nunito, SweetAlert2, bootstrap.bundle).

  $funciones->menuLateral2($idUsuarioSession, $idPagActual)
        Renderiza el menu lateral (offcanvas/sidebar) segun permisos del
        usuario (tablas permisos_menu_1 / menu_1 / menu_1_sub). $idPagActual
        marca el item activo. (Existe tambien menuLateral() y
        menuLateral2Antiguo() como versiones historicas.)

  $funciones->cabezera()
        Barra superior (topbar): nombre del usuario, notificaciones, avatar,
        acceso a perfil / cerrar sesion.

  $funciones->footer()
        Pie de pagina + scroll-to-top.

  $funciones->script()
        Imprime JS global de cierre: bootstrap.bundle, jquery.easing,
        sb-admin-2.min.js, Chart.min.js, chart-area-demo.js, SweetAlert2,
        js/funciones.js, flatpickr.

  Contenedores de estado (tarjetas KPI). Cada uno hace 3 consultas:
  COUNT de tickets en ese estado (segun idPagActual), COUNT total, y
  SELECT color_degradado / descripcion_estado de la tabla estados_ticket.
  Renderiza una tarjeta con contador, porcentaje, barra de progreso, popover
  con la descripcion del estado y una lupa que llama filtrarTickets(idEstado).

        $funciones->contenedorTicketRecibidos($id, $idPag)   estado 1  (SOLO admin)
        $funciones->contenedorTicketAsignados($id, $idPag)    estado 2  (las 3 vistas)
        $funciones->contenedorTicketEnProceso($id, $idPag)    estado 3  (las 3 vistas)
        $funciones->contenedorTicketTerminados($id, $idPag)   estado 5  (las 3 vistas)
        $funciones->contenedorTicketDemorados($id, $idPag)    estado 7  (las 3 vistas)
        (existen tambien contenedorTicketCerrados=6 y contenedorTicketBorrador=4,
         no usados en estas 3 vistas)

  Logica del contador segun $idPagActual dentro de cada contenedor:
        idPag == 4 (admin)  : WHERE id_estado = X            / total = todos
        idPag == 5 (tecnico): WHERE id_estado = X AND id_tecnico = sesion
        idPag == 3 (usuario): WHERE id_estado = X AND id_usuario = sesion
        idPag == 8          : igual que usuario (otra vista)

Invocados dentro de los includes bloque_tabla_* :

  $funciones->ticketUsuario($idUsuarioSession, $estado = null)
        SELECT de tickets del usuario (t.id_usuario = sesion).
        JOIN estados_ticket, usuarios; LEFT JOIN proceso_tickets,
        calificacion_tickett. Subconsultas para contar
        archivos_adjuntos_ticket, conversaciones, ticket_conversaciones
        (total y no leidos por el usuario).
        GROUP BY t.id_ticket, ORDER BY fecha/hora_creacion_inicio DESC.
        Si $estado != null agrega AND t.id_estado = $estado.

  $funciones->obtenerTicketsTecnico($idUsuarioSession, $estado = null)
        SELECT de tickets donde t.id_tecnico = sesion AND t.id_estado != 4.
        JOIN estados_ticket, usuarios (solicitante); LEFT JOIN usuarios
        (tecnico), proceso_tickets, conversaciones, calificacion_tickett,
        ticket_conversaciones. COUNT de mensajes / conversaciones / adjuntos.
        Trae calificacionEstrellas (ct.id_calificacion).

  $funciones->ticketAdministrador($idUsuarioSession, $estado = null)
        SELECT de TODOS los tickets con t.id_estado != 4.
        Mismos JOIN que la del tecnico pero sin el WHERE por tecnico.
        Trae nombreTecnico / apellidoTecnico, tieneCalificacion,
        cantidadArchivos, cantidadConversaciones.

  $funciones->actualizarTicketsDemoradosAutomaticamente()
        NO se llama desde estos 3 archivos (se llama en principal.php), pero
        es la que mueve a estado 7 los tickets con id_estado IN (2,3) cuya
        pt.fecha_estimada_admin < CURDATE(). Es el "cron manual" que explica
        por que aparecen tickets Demorados en estas vistas.

Helpers internos usados por los bloques:
  $funciones->obtenerColorEstado($id_estado)   (mapa fijo de colores 1/2/3/5)

        - actualizarTablaAdministrador(): guarda actualizacionTablaEnCurso,
          $.post a componentes/ajax/bloque_tabla_adminn.php  <-- (ver BUG 1.3)
          con { idUsuarioSession, vista:'ticket_admin', [estado] }. Compara
          html normalizado y solo redibuja si cambio; luego
          renderizarCalificacionesTablaAdmin(). .always() libera el flag.
        - setInterval(actualizarTablaAdministrador, 3000).
        - window.filtrarTickets(estado): hace su PROPIO $.post inmediato
          (no reusa actualizarTablaAdministrador) con vista:'ticket_admin'.
        - window.mostrarTodosLosTickets().
  (3) function mostrarOffcanvasAsunto(idTicket): igual que en ticket.php.

  En bloque_tabla_adminn.php ademas hay JS inline:
        - DOMContentLoaded: inicializa tooltips de Bootstrap.
        - function enviarAvisoUltimoDiaTecnico(idTicket): SweetAlert2 de
          confirmacion + $.ajax POST modelos/guardar/avisar_ultimo_dia_tecnico.php.
        - Duplicado de asignacionTecnico y del plugin de filtros admin.

--------------------------------------------------------------------------------
3.4  Patron comun del auto-refresco (las 3 vistas)
--------------------------------------------------------------------------------
    1. Estado local: tabla (instancia DataTable), filtroActivo (bool),
       estadoFiltrado (int|null), ultimaHuella/ultimaTablaAdminHtml (string).
    2. Cada 3000 ms: POST al endpoint AJAX del bloque correspondiente.
    3. Del HTML devuelto se toma SOLO  #<tablaId> tbody  con jQuery.
    4. Se normaliza (.replace(/\s+/g,' ').trim()) y se compara con la ultima
       huella. Si es igual -> return (no se toca el DOM, no hay parpadeo).
    5. Si cambio -> tabla.clear(); tabla.rows.add(filasNuevas); tabla.draw(false).
       draw(false) mantiene la pagina actual del paginador.
    6. El filtro por KPI (filtrarTickets) manda el parametro 'estado' al backend
       (filtro server-side), mientras que los <select>/<input date> de arriba de
       la tabla filtran client-side via ext.search.push (filtro DOM).

6. COMO FUNCIONAN LOS "CONTENEDORES" DE TICKETS
================================================================================

Hay DOS conceptos distintos que en el codigo se llaman "contenedor":

--------------------------------------------------------------------------------
6.1  Contenedores de ESTADO  (tarjetas KPI de la parte superior)
--------------------------------------------------------------------------------
  <div class="contenedor-estados-ticket" id="idContenedoresEstadosTicket">
     ... aqui se pintan las tarjetas ...
  </div>

  Cada tarjeta la genera un metodo de Funciones:
     contenedorTicketRecibidos  (estado 1) -- SOLO en ticket_admin_v2.php
     contenedorTicketAsignados  (estado 2)
     contenedorTicketEnProceso  (estado 3)
     contenedorTicketTerminados (estado 5)
     contenedorTicketDemorados  (estado 7)   (titulo visible: "Tickets Atrasados")

  Que hace cada metodo (mismo esqueleto):
     1. $bdato = new MySQL("","","")
     2. Segun $idPagActual arma 2 consultas:
          - $sql      = COUNT de tickets EN ESE ESTADO (con el filtro del rol)
          - $sqlTotal = COUNT de tickets del rol (sin filtro de estado)
        idPag 4 -> sin filtro de propietario (admin ve todo)
        idPag 5 -> AND id_tecnico = sesion
        idPag 3 / 8 -> AND id_usuario = sesion
     3. $porcentaje = round(contador / max(1,total) * 100)
     4. SELECT color_degradado, descripcion_estado FROM estados_ticket WHERE id = <estado>
        (si viene vacio usa un degradado por defecto)
     5. Pinta:
          <div class="tarjeta-ticket-estado fade-in [estado-atencion]"
               style="background: <degradado>">
             titulo + "contador (porcentaje%)" con tooltip "X de Y"
             icono (bootstrap-icon) con popover = descripcion_estado
             barra de progreso Bootstrap con width = porcentaje%
             footer con  <i class="bi bi-search" onclick="filtrarTickets(<estado>)">
     6. La clase 'estado-atencion' solo la agrega contenedorTicketRecibidos
        cuando contador >= 1 (resalta que hay tickets sin asignar).

  Interaccion:
     - Click en la lupa -> window.filtrarTickets(idEstado).
       filtrarTickets es un TOGGLE: si el filtro ya estaba en ese estado, lo
       apaga (vuelve a "todos"); si no, lo enciende.
     - Cuando el filtro esta activo, el parametro 'estado' viaja en el $.post
       del refresco de la tabla -> el backend (ticketUsuario /
       obtenerTicketsTecnico / ticketAdministrador) agrega
       "AND t.id_estado = <estado>" a su SQL. Es un filtro SERVER-SIDE.
     - No hay boton visible de "mostrar todos": se consigue volviendo a pulsar
       la misma lupa (toggle) o llamando window.mostrarTodosLosTickets().

--------------------------------------------------------------------------------
6.2  Contenedor de la TABLA  (card + <div id="contenedorTabla*">)
--------------------------------------------------------------------------------
  ticket.php            -> <div id="contenedorTablaUsuario">   include bloque_tabla_usuario.php
  ticket_asignados.php  -> <div id="contenedorTablaTecnico">   include bloque_tabla_tecnico.php
  ticket_admin_v2.php   -> <div id="contenedorTablaAdmin">     include bloque_tabla_adminn.php

  Estos DIV son el "contenedor" donde:
     - en la carga inicial PHP escribe la tabla completa (filtros + <table>).
     - en el refresco AJAX el JS reemplaza SOLO el <tbody> del DataTable
       (no reemplaza el div entero, para no perder la instancia de DataTable
       ni el foco de los filtros).

  Estructura interna de cada tabla:
     - Un bloque de filtros (div.ticket-admin-filtros) con <select>/<input date>.
     - <table id="..."> con <thead class="table-dark"> y <tbody> generado en un
       while ($row = $resultado->fetch_array()).
     - Cada <tr> lleva data-attributes que consumen los filtros client-side:
          data-estado, data-fecha-creacion (Y-m-d), data-tecnico-id,
          data-fecha-respuesta (Y-m-d).
     - Cada <tr> tiene una clase estado-ticket-<id_estado> y (en modo admin
       compacto / usuario) la clase fila-ticket-admin-compacta.
     - El color del estado se muestra como:
          * modo normal admin  -> toda la fila/celdas con background-color del estado
          * modo compacto (ticketAdminColorColumn=true, y siempre en usuario/tecnico)
            -> un puntito <span class="estado-indicador-dot"> en la celda ID.

6.3  Contenedor del CHAT
--------------------------------------------------------------------------------

  chat_ticket.js -> cargarTicketConversacion() inyecta ahi un
  <div class="offcanvas offcanvas-end" id="offcanvasTicket"> con

================================================================================
7. FILTROS Y BUSQUEDAS
================================================================================

--------------------------------------------------------------------------------
7.1  Filtro por KPI (server-side)  -- las 3 vistas
--------------------------------------------------------------------------------
  Disparador : lupa <i class="bi bi-search" onclick="filtrarTickets(N)"> en el
               footer de cada tarjeta de estado.
  N          : 1 Recibido, 2 Asignado, 3 En proceso, 5 Terminado, 7 Demorado.
  Mecanismo  : window.filtrarTickets(estado) hace toggle de {filtroActivo,
               estadoFiltrado} y dispara el refresco de tabla. El estado viaja
               como parametro POST 'estado' -> el metodo SQL agrega
               AND t.id_estado = <estado>.
  Quitar     : volver a pulsar la misma lupa, o window.mostrarTodosLosTickets().
  Persistencia: NO (se pierde al recargar).

--------------------------------------------------------------------------------
7.2  Filtros de cabecera de tabla (client-side, DataTables ext.search)
--------------------------------------------------------------------------------
  Se registra UNA vez por vista un callback en
  $.fn.dataTable.ext.search.push(function(settings,data,dataIndex){...})
  que solo actua sobre su tabla (comprueba settings.nTable.id) y decide
  mostrar/ocultar cada fila comparando los <select>/<input> con los
  data-attributes del <tr>. Al cambiar cualquier filtro se llama tabla.draw().

  ticket.php  (#tablaUsuario) -- controles:
     #filtroEstadoUsuario  (Todos / Asignado / En proceso / Terminado /
                            Borrador / "Atrasado" -> se normaliza a "demorado")
     #filtroFechaUsuario   (input date, compara con data-fecha-creacion)
     #filtroFechaRespuestaUsuario (input date, vs data-fecha-respuesta)
     #filtroTecnicoUsuario (referenciado en el JS del filtro pero el <select>
                            NO se pinta en bloque_tabla_usuario.php -> filtro
                            de tecnico inactivo en la vista usuario)
     Helper: configurarFiltrosTablaUsuario(dt); flag data('usuario-filters-bound').

  ticket_asignados.php  (#tablaTecnicoTicketAsignados) -- controles:
     #filtroEstadoTecnico  (Todos / Asignado / En proceso / Terminado /
                            "Atrasado"->demorado / Cerrado)
     #filtroFechaTecnico            (vs data-fecha-creacion)
     #filtroFechaRespuestaTecnico   (vs data-fecha-respuesta)
     Persistencia: SI, en sessionStorage clave 'filtrosTablaTecnico'
        (guardarFiltrosTecnico / restaurarFiltrosTecnico).
     Al cambiar filtros se llama guardarFiltrosTecnico() + dt.draw().

  ticket_admin_v2.php  (#dataTableAdministrador) -- controles:
     #filtroEstadoAdmin    (Todos / Recibido / Asignado / En proceso /
                            Terminado / "Atrasado"->demorado / Cerrado)
     #filtroFechaAdmin             (vs data-fecha-creacion)
     #filtroTecnicoAdmin   (Todos / "Sin asignar" = valor __sin_asignar__ /
                            uno por cada tecnico id in [6,7,8,42]);
                            compara con data-tecnico-id de la fila
                            ('' = sin asignar)
     #filtroFechaRespuestaAdmin    (vs data-fecha-respuesta)
     Helper: configurarFiltrosTablaAdmin(); flag data('admin-filters-bound').
     Registro unico: window.adminTableFiltersSearchRegistered.

  Normalizacion comun: la opcion mostrada como "Atrasado" tiene value
  "Demorado"; el JS baja a minusculas y convierte "atrasado" -> "demorado"
  para casar con data-estado (que trae et.nombre = "Demorado").

--------------------------------------------------------------------------------
7.3  Buscador de texto libre (js/buscadores.js)
--------------------------------------------------------------------------------
  Escucha input en #idBuscarmensaje, #idBuscarTicket,
  #buscar_ticketAdministrador, #buscarUsuario y oculta filas cuyo texto
  concatenado no contenga el termino. En estas 3 vistas practicamente no se
  usa porque las tablas tienen el buscador propio de DataTables; queda cargado
  por herencia de otras pantallas.

--------------------------------------------------------------------------------
7.4  Buscador nativo de DataTables
--------------------------------------------------------------------------------
  Cada tabla se inicializa con DataTable({ language: es-ES, responsive:true,
  pageLength:10 }) -> aporta su propio input "Buscar:", ordenamiento por
  columna y paginacion. En admin ademas pagingType:'simple_numbers'.
  El refresco usa draw(false) para no perder la pagina activa.

--------------------------------------------------------------------------------
7.5  Filtro fijo por rol (siempre activo, en el SQL)
--------------------------------------------------------------------------------
  usuario  : WHERE t.id_usuario = sesion
  tecnico  : WHERE t.id_tecnico = sesion AND t.id_estado != 4
  admin    : WHERE t.id_estado != 4         (todos menos borradores)
  Ademas todas ORDER BY pt.fecha_creacion_inicio DESC, pt.hora_creacion_inicio DESC
  y GROUP BY t.id_ticket.

8. VALIDACIONES
================================================================================

--------------------------------------------------------------------------------
8.1  Validaciones de sesion / acceso
--------------------------------------------------------------------------------
  - Las 3 vistas asumen sesion iniciada: usan htmlspecialchars($_SESSION['id']).
    Si $_SESSION['id'] no existe -> warning/fatal PHP (no hay redireccion a
    login en el propio archivo; se delega en el include de conexion/funciones o
    en el .htaccess del proyecto).
  - bloque_tabla_tecnico.php SI valida: si !$idUsuarioSession hace
    session_start() y, si sigue vacio, imprime
    "<tr><td colspan='8'>ID del tecnico no definido.</td></tr>" y return.
  - Endpoints AJAX (componentes/ajax/bloque_tabla_*.php): si no llega
    $_POST['idUsuarioSession'] -> echo "ID de usuario no recibido." ; exit.
  - El control de QUE puede ver cada rol es por el WHERE del SQL (id_usuario /
    id_tecnico / todos), no por comprobacion de perfil. El acceso al archivo
    en si depende del menu/permisos (permisos_menu_1) y del idPagActual.

--------------------------------------------------------------------------------
8.2  Saneo de entrada / salida (server-side)
--------------------------------------------------------------------------------
  - htmlspecialchars() sobre id, nombre, apellido, id_area_trabajo de sesion.
  - En los bloques: (int)$row['id_ticket'], (int)$row['id_estado'],
    intval($idUsuarioSession) antes de interpolar en SQL de los contenedores.
  - htmlspecialchars() en casi todos los ecos de datos de fila (asunto,
    nombreEstado, colorEstado, fechas formateadas, textos de estado).
  - Filtro de tecnicos: implode(',', array_map('intval', $tecnicosFiltroIds)).
  - OJO: ticketUsuario / obtenerTicketsTecnico / ticketAdministrador
    interpolan directamente "$idUsuarioSession" y "$estado" en el SQL
    (concatenacion de strings, sin prepared statements). Los endpoints AJAX
    los pasan por intval() antes, pero la ruta por carga directa de pagina
    depende de que $_SESSION['id'] sea confiable. -> ver seccion 8.6.

--------------------------------------------------------------------------------
8.3  Validaciones al CREAR ticket  (crearTicketGuadalupe / enviarDatosTicket, ticket.js)
--------------------------------------------------------------------------------
  preConfirm del modal:
     - 'asunto' obligatorio (trim != "") -> si no, clase .input-error.
     - 'categoria' obligatoria (select con value) -> .input-error.
     - 'descripcion': se valida el TEXTO plano del editor Quill
       (editorDescripcion.getText().trim()); si vacio -> .input-error y borde
       rojo en .ql-container.
     - Si algo falla -> Swal.showValidationMessage('Debes completar todos los
       campos obligatorios') y no se envia.
  didOpen: al escribir/cambiar en asuntoTicket / descripcionTicket /
     selectCategoria se quita la clase .input-error (feedback en vivo).
  Ruteo por categoria: si selectCategoria === "10" el endpoint es
     guardar_ticket_sin_tecnico.php (regla de negocio, no validacion de forma).
  Estado resultante: Confirm -> 1 ; Deny -> 4 (borrador, se guarda igual pero
     el borrador NO exige las mismas validaciones estrictas -> se envia con lo
     que haya, ojo).
  Adjuntos: validandoFormatoDeAdjunto("archivoTicket","contenedorArchivos",
     "badgeArchivos") valida extension/tamano y arma la lista visual;
     actualizarListaArchivos() sincroniza el input con un DataTransfer.

--------------------------------------------------------------------------------
8.4  Validaciones al ASIGNAR tecnico  (asignacionTecnico, ticket_admin_v2.php)
--------------------------------------------------------------------------------
  preConfirm:
     - 'tecnicoSeleccionado' (hidden) obligatorio.
     - 'categoriaTicket' obligatoria.
     - Si falta alguno -> Swal.showValidationMessage('Debe seleccionar tecnico
       y categoria') y return false.
  El comentario al tecnico es opcional.
  sanitizarDescripcionHtml(): antes de mostrar la descripcion del ticket en el
     modal, recorre el DOM y elimina toda etiqueta que no este en la whitelist
     {BR,P,OL,UL,LI,B,STRONG,I,EM,U} y borra TODOS los atributos -> proteccion
     XSS basica del contenido rich-text.

--------------------------------------------------------------------------------
8.5  Validaciones al CALIFICAR  (validacionTicketPorUsuario, validacionTicket.js)
--------------------------------------------------------------------------------
  - Debe haberse seleccionado una estrella: si !calificacionId ->
    se muestra #mensajeError y se pone borde rojo
    (.contenedor-estrellas-error) en #estrellasWrapper; resolve(false)
    para que SweetAlert2 no cierre ni bloquee el boton.
  - El comentario es OPCIONAL (el bloque que lo exigia esta comentado).
  - allowOutsideClick:false y allowEscapeKey:false -> el usuario no puede
    esquivar la calificacion cerrando el modal.
  - Respuesta del backend: si response.success -> mostrarModalNegativo(),
    si no -> Swal error; el .error del ajax hace fallback a
    mostrarModalPositivo(). Ambos modales terminan en location.reload().
  Visibilidad del boton: solo aparece si id_estado === 5 && empty(tieneCalificacion)
  (se controla en PHP en bloque_tabla_usuario.php).

--------------------------------------------------------------------------------
8.6  Validaciones al REPROGRAMAR fecha (ticket demorado)
--------------------------------------------------------------------------------
  reprogramarFechaTicketDemorado(id, fechaActualIso): el modal exige elegir una
  fecha nueva; si fechaActual viene vacia se muestra "Sin fecha definida".
  El backend recalcula dias_estimada_admin como diferencia entre
  proceso_tickets.fecha_creacion_inicio y la nueva fecha_estimada_admin
  (regla del CLAUDE.md: no viene del JS).

--------------------------------------------------------------------------------
8.7  Validaciones del refresco AJAX (anti-parpadeo / anti-solape)
--------------------------------------------------------------------------------
  - Comparacion de "huella" del <tbody> normalizada: si no cambio, no se
    redibuja (evita perder seleccion/scroll y reduce carga).
  - typeof nuevoTbody === 'undefined' -> return (respuesta invalida/parcial).
  - admin: flag actualizacionTablaEnCurso (+ .always) para que no se solapen
    dos peticiones de 3 s.
  - Registro unico de plugins de filtro con banderas window.*Registered y
    data('*-filters-bound') para no duplicar listeners en cada refresco.

--------------------------------------------------------------------------------
8.8  Observaciones / riesgos (no son validaciones, pero conviene documentarlos)
--------------------------------------------------------------------------------
  (a) ticket_admin_v2.php pide 'componentes/ajax/bloque_tabla_adminn.php'
      (doble n) pero el archivo es 'bloque_tabla_admin.php' (una n) ->
      el auto-refresco de la tabla admin probablemente falla (404).
  (b) header() carga Bootstrap 5.1.3 y SweetAlert2, y ademas cada vista vuelve
      a cargar Bootstrap 5.3.3 + 5.3.2 bundle y SweetAlert2 -> multiples
      versiones de Bootstrap conviviendo (posibles inconsistencias de JS/CSS).
  (c) Las consultas ticketUsuario / obtenerTicketsTecnico / ticketAdministrador
      concatenan valores en el SQL (sin binding). Mitigado en la ruta AJAX por
      intval(), pero no es defensa en profundidad.
  (d) js/chat_ticket.js hace una llamada AJAX sincrona (async:false) por cada
      mensaje para resolver el nombre del emisor -> puede congelar la UI en
      conversaciones largas.
  (e) asignacionTecnico() esta definida dos veces (inline en ticket_admin_v2.php
      y dentro de bloque_tabla_adminn.php) -> la ultima cargada gana.
  (f) calificarTicket() en ticket.js muestra fecha/hora HARDCODEADAS
      ("2025-06-11" / "14:32:00") en el modal de solo lectura, en lugar de
      data.data.fecha / data.data.hora.
  (g) El link "Historial del Ticket" del menu de 3 puntos apunta a
      estadistica/vida_ticket.php sin el ?id_ticket=... (la version con el
      parametro esta comentada).
  (h) El buscador de js/buscadores.js y los data-intro de Intro.js siguen en
      el HTML aunque sus botones esten comentados.
