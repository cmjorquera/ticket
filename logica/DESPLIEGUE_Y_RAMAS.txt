DESPLIEGUE Y RAMAS – cómo subir cambios a QA
=============================================
Actualizado: 2026-11-26

Resumen
-------
  rama qa   --deploy_qa.sh-->   QA          https://sistemabase.webnia.cl   (probar)
  rama main --deploy_prod.sh--> PRODUCCIÓN  https://acceso.seduc.cl         (usuarios reales)

Todo cambio va primero a "qa" y se prueba en QA. Cuando funciona, se une qa en
main y se publica en producción. Hacer push NO publica nada por sí solo.

2. Camino A: Claude hace el cambio
----------------------------------
Claude hace el cambio y el push directo a qa en GitHub.

  1) Pedir el cambio indicando: "rama qa de github.com/cmjorquera/ticket".
  2) Claude responde con el número de commit (ej. 389c00a).
  3) En VS Code de SISTEMA_CENTRAL_SEDUC, bajar el cambio:

       git switch qa
       git pull
       git log --oneline -1      # debe mostrar el commit que dio Claude

  4) Publicar en QA (punto 4).

  Si hay cambios propios sin subir antes del git pull, subirlos primero
  con el Camino B; si no, el pull puede fallar.


3. Camino B: yo hago el cambio y hago push
------------------------------------------
  1) Bajar lo último (por si Claude hizo cambios):

       cd C:\Users\cmjor\Documents\SISTEMA_CENTRAL_SEDUC
       git switch qa
       git pull

  2) Hacer los cambios en VS Code y guardarlos.
  3) Revisar qué cambió:

       git status
       git diff

  4) Guardar en git y subir:

       git add .
       git commit -m "describe aquí el cambio"
       git push

  5) Publicar en QA (punto 4).

  No subir .zip ni respaldos: si git status los muestra, sacarlos antes del git add.


4. Publicar en el servidor QA
-----------------------------
  1) En la terminal de VS Code (línea "PS C:\..."):

       ssh ticket-qa

  2) Cuando la línea diga  crist668@webnia.cl [~]#  ya se está en el servidor.
     Simular (no modifica nada):

       ~/repositories/ticket/scripts/deploy_qa.sh --dry-run

  3) Revisar el resumen: commit, archivos que se reemplazan y nuevos.
  4) Publicar de verdad (escribir "si" cuando lo pida):

       ~/repositories/ticket/scripts/deploy_qa.sh --ejecutar

  5) Abrir https://sistemabase.webnia.cl y recargar con Ctrl+F5.
  6) Salir del servidor:  exit

  El script respalda antes de publicar, nunca borra archivos y no toca
  uploads, imágenes, QR, logs ni la base de datos.
  Si el cambio trae un .sql, se ejecuta aparte en phpMyAdmin (QA y luego producción).


5. Deshacer (rollback)
----------------------
  ~/repositories/ticket/scripts/rollback_qa.sh                  # lista los respaldos
  ~/repositories/ticket/scripts/rollback_qa.sh <ID> --ejecutar   # deshace ese despliegue

  El ID lo muestra el deploy al terminar (ej. 20261126_061540).


6. Problemas comunes
--------------------
  "deploy_qa.sh no se reconoce como cmdlet"
      -> se escribió en el PC (PS C:\...). Primero ssh ticket-qa.
  "Your local changes ... would be overwritten"
      -> hay cambios sin guardar. git status; subirlos (Camino B) o
         descartarlos con: git restore <archivo>
  git push rechazado
      -> hay cambios nuevos en GitHub: git pull y luego git push.
  El sitio no muestra el cambio
      -> Ctrl+F5; revisar que se corrió --ejecutar.
  Rename-Item "being used by another process"
      -> VS Code tiene la carpeta abierta: cerrarlo o reiniciar el PC.


7. Pasar a PRODUCCIÓN (acceso.seduc.cl)
---------------------------------------
Solo cuando el cambio ya funciona en QA.

  1) Unir qa en main. Pedírselo a Claude ("pasa qa a main"), o en el PC:

       git switch main
       git pull
       git merge qa
       git push
       git switch qa          # volver a trabajar en qa

  2) Publicar (en la terminal de VS Code):

       ssh seduc-prod
       ~/repositories/sistema-central-seduc/scripts/deploy_prod.sh --dry-run
       ~/repositories/sistema-central-seduc/scripts/deploy_prod.sh --ejecutar

  3) Revisar https://acceso.seduc.cl con Ctrl+F5.

  Deshacer:
       ~/repositories/sistema-central-seduc/scripts/rollback_prod.sh
       ~/repositories/sistema-central-seduc/scripts/rollback_prod.sh <ID> --ejecutar

  Si el cambio trae un .sql: ejecutarlo en phpMyAdmin de producción
  ANTES de --ejecutar (salvo que el código funcione sin él).
